# Architecture

> Public source edition: three agency photographs and their display captions were replaced with original, disclosed AI-generated illustrations. This snapshot differs visually from the linked live competition build. Historical phase results below describe their named phases; current verification is in [PUBLIC_EDITION_VERIFICATION.md](../PUBLIC_EDITION_VERIFICATION.md).

PARALLAX is a static React/TypeScript application built with Vite. All individual observations are fictional; published evidence remains separately typed. State stays in browser memory, localStorage or bounded IndexedDB; exports are generated locally.

`App.tsx` coordinates Mission, Discover, guided scenarios, Research and the Advanced workspace. Mission, guided presentation, Discover, Research and Advanced load through route-level dynamic imports. Guided investigations own their state through `site/guidedState.ts`; transferring a case into a modified workspace requires confirmation. `?evaluation=1` opens the neutral workspace without introductory scenarios or answer-bearing teaching material. `workspace/Workspace.tsx` presents Health Monitor, Observations, Evidence Lens, Health Actions and Science & sources.

| Module                  | Responsibility                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------ |
| `web/src/core/model.ts` | Typed synthetic observation and finding contracts                                    |
| `core/validate.ts`      | Bounded atomic input validation, units, dependencies, timestamps and declared origin |
| `core/engine.ts`        | Direct-pair compatibility, descriptive arithmetic and scope boundaries               |
| `core/entry.ts`         | Validated record entry and update                                                    |
| `core/context.ts`       | Review-phase explanations while retaining acquisition identity                       |
| `core/actions.ts`       | Finding-specific information-management actions and review receipts                  |
| `core/session.ts`       | Validated persistence, migration and one-step Undo                                   |
| `core/review.ts`        | Current findings, provenance, gaps and review question in Markdown                   |
| `src/data/`             | Fictional fixtures and separately typed scientific context                           |
| `src/site/`             | Guided navigation, source exploration and chart presentation                         |

Paths abbreviated after the first row are relative to `web/src/`. Views, action rules and exports consume the same engine findings. Reviewing a question or completing a fictional prescribed-plan activity cannot add evidence. Receipts apply only while their evidence signature remains current.

Published research has a distinct data type and cannot enter a `CasePacket` as an individual observation. Loading a review phase cannot convert a ground or bed-rest record into an in-flight record. The application has no fitted model, network data API, remote LLM or physical-device adapter.

`build-offline.mjs` creates a same-origin service-worker cache keyed to production asset content. The cache supports reload and local work after installation. External scientific pages remain external links. [Methods](METHODS.md) describes the calculation and acquisition rules.

## Mission foundation

The default route and `#mission` open the Mars premise; `#mission/health` opens its overview. `#discover`, `#scenarios`, `#research` and the five workspace routes remain available. Evaluation routing runs before site routing, so mission and guided teaching cannot render under `?evaluation=1`.

| Module                    | Responsibility                                                                                                                                           |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mission/context.ts`      | Validated fictional identity, four-phase timeline, gravity, activity, resources, illustrative Earth communications and revision                          |
| `mission/observations.ts` | Two quantity-specific fictional assessment definitions, immutable source fixtures, origin-separated research/device contracts and acquisition validation |
| `mission/bridge.ts`       | Explicit selected assessment IDs mapped to a validated legacy packet and the unchanged evaluator; no telemetry selection or reduction                    |
| `mission/requirements.ts` | Three bounded review questions, equipment/supervision restrictions and source locators                                                                   |
| `mission/state.ts`        | One reducer, validated resume and the dedicated `parallax.mission.v1` storage namespace                                                                  |
| `mission/overview.ts`     | Shared projection for chart, observations, scoped coverage and actual fictional disposition                                                              |
| `mission/Mission.tsx`     | Mission shell and hero, with a lazy health workspace and review desk                                                                                     |

Fictional observations retain value/unit, source identity, protocol/session/window, fictional UTC acquisition time, phase/gravity, direct/derived status, quality and provenance. Only defined HR and force assessment quantities enter the new bridge. Research, documented-format synthetic telemetry, future authorised recorded replay and approved live hardware have separate origins; none can enter that bridge. The separately lazy-loaded devices module implements a bounded synthetic commercial Astroskin HR/quality adapter; see DEVICE_FORMATS.md. Its in-memory batch and revision-bound association never modify mission evidence. The isolated research aggregate function reads a licensed public numerical register. The planner supports validated fictional archive retrieval only.

The evaluator remains authoritative for descriptive comparisons. The bridge preserves its packet validation and uses explicit selected IDs; it never chooses the latest sample or averages streams. The mission projection additionally checks phase applicability: a historical transit comparison cannot become a current Mars assessment. Source records survive exclusion. Interpretation, monitoring designations and fictional review snapshots consume this same mission state. Bounded adapter replay and same-profile companion event delivery live in the lazy `monitoring/` modules; see DEVICE_FORMATS.md.

Reload restores validated mission state. Schema 2 now has a bounded `reviewSchemaVersion: 1` extension; Phase 2 selections migrate without inventing a designation or review. Schema 1 still resets visibly. Restart starts a new session UUID and initial active membership while retaining the latest five review snapshots and five monitoring designations as historical. Eviction counts are explicit. Invalid saved records trigger a visible reset; a changed fixture starts a fresh generation while retaining valid bounded histories. Storage denial permits in-memory work under the same writer ownership.

`mission/identity.ts` binds mission, astronaut, session UUID, context/evidence revisions, fixture and source/interpretation/monitoring/review-policy versions. Its exact canonical evidence/context key includes original records, selected/excluded IDs and mutation lineage. A short FNV-1a fingerprint is a display aid, never the equality authority or authentication. A new UUID lineage accompanies every evidence/context mutation, so divergent tabs and restored numbers cannot equate solely through incrementing revisions. All such mutations conservatively invalidate all plan items; the plan-set revision and exact saved plan-set contents also determine review currency. A no-op retrieval or designation leaves currency unchanged.

`mission/review.ts` creates and recursively freezes complete fictional snapshots. A bounded enum selects disposition, reasons and human priority; no personal name or free medical prose is requested. Stored snapshot validation checks structure, origins, times, identity and sources; current-version generated content must match the bundled source evidence and templates. Older version-labelled snapshots retain their original content and are stale. Browser-local contents remain editable and unauthenticated.

`mission/handoff.ts` derives a canonical handoff envelope with the saved snapshot, current currency and export creation time. The preview, escaped HTML document and JSON download consume the same object. No Markdown parser reconstructs findings. Currency metadata can change while snapshot contents stay fixed. The existing Advanced export is independent.

`mission/writer.ts` is the only mission persistence boundary. A named Web Lock grants one cooperating mission surface editing ownership until unmount; other tabs follow storage changes read-only. The owner rereads under the lock before initialisation and compares exact expected storage bytes before each synchronous write. Unexpected storage changes stop edits without overwriting them. No lock support means read-only mission access. The companion uses a narrow transaction boundary for validated receipts and acknowledgments; it never writes mission records. Replay ingestion requires mission ownership. There is no atomic transaction across localStorage and IndexedDB; every live association is revalidated against current saved mission identity.

Web Locks coordinate cooperating same-origin contexts only. The storage comparison is not atomic compare-and-swap against old/noncooperating scripts; one can write between check and commit. Storage events are notifications, not transactions. Locks do not establish cross-device consistency, authenticated identity, background availability or durable clinical storage. No multiwriter merge is claimed.

Guided state is written only following a guided mutation; simply visiting Mission or evaluation does not rewrite it. The mission cannot edit workspace imports, marks, questions, receipts or evaluation data. No external dependency was added. The original Mars graphic is local SVG; numerical charts use SVG with text/table alternatives and reduced-motion support.

## Assessment planner and archive boundary

`mission/archive.ts` keeps the obtained 28 June fixture separate from active review membership and validates every source field before retrieval. `includedRecordIds` is distinct from `excludedRecordIds` (a subset of included records). `overview.ts` passes only included, selected records into the unchanged evaluator. Removing retrieval removes membership; excluding a retrieved record retains membership and source identity. No entered number can inherit archive provenance.

`mission/assessments.ts` holds seven selected assessment areas and a pure applicability evaluator. It retains simultaneous blockers for phase, gravity, measurement definition, data origin, source/evidence support, equipment, qualified assistance, supervision and approved protocol. Availability never grants permission for a physical test. Only the obtained fictional cycling record can be collected. `Planner.tsx` renders the same state projection used by the overview and summary; source details are shared with `Records.tsx`.

The mission entry, health workspace and interpretation/review desk load separately. Installed offline caching still includes every chunk. No runtime dependency was added.

Phase 3’s measured code/text/graphics limit is 650,000 bytes and total static limit is 1,350,000 bytes; Phase 2 limits were 600,000 and 1,300,000. The additional models, validation, review interactions and exports exceed those earlier limits. Photography stays at most 750,000 bytes, every JS asset below 400,000 and fresh mission-entry JavaScript at most 350,000. These remain below the authorised total/code ceilings; release verification reports actual bytes.

## Monitoring module boundaries

`monitoring/fixture.ts` authors one coherent relative-clock recording. `model.ts` defines run identity, retention, sample idempotency, quality episodes and recovery; `semantics.ts` defines event meanings. `store.ts` performs bounded validated IndexedDB transactions and narrow companion actions. `controller.ts` owns deterministic foreground execution and checks identity after asynchronous parsing. `MonitoringConsole.tsx`, `Companion.tsx` and `EventHistory.tsx` render authoritative data. `transport.ts` validates small wake-up/heartbeat messages; arbitrary broadcast event bodies cannot enter the ledger. `snapshot.ts` defines compact immutable review evidence and historical validation. The original assessment bridge/evaluator never receives telemetry.

The mission review-policy version is now `fictional-review-2`. Earlier snapshots keep their original versions/content and become stale against the new policy; no old record is rewritten. Monitoring snapshot schema 1 / `monitoring-review-1` evolves independently. An older review without this field remains valid history.

Phase 5 historically enforced total static output below 1,430,000 bytes and code/text/graphics below 720,000 after measured growth from 1,360,000/650,000. The approved upper ceilings remain 1,500,000/750,000 for future reviewed work. Photography stays at most 750,000 bytes, each JS asset below 400,000 and fresh mission-entry JS at most 350,000. All lazy assets count toward the complete offline payload.

The bounded mission object still stores only five designations and five immutable review snapshots, including compact latest-run monitoring evidence. A worst-case five-review/five-designation save measured about 378,000 characters, so Phase 5 raises the guarded review-object limit from 300,000 to 500,000 characters and checks it on both encode and decode. Live samples/events remain in the separate bounded IndexedDB stores; this is not a localStorage telemetry stream.

The current release gates require total static output below 1,510,000 bytes, code/text/graphics below 800,000, photographs at most 750,000, each JavaScript asset below 400,000 and fresh mission-entry JavaScript at most 350,000. The complete verifier measures the full source-bound evaluation record. An ordinary build's placeholder is not evidence of release payload compliance.

The assessment planner uses one vertical tablist for all seven options, with visual group headings and one selected detail panel. Arrow keys cross the visual groups; Home/End select the first/last option. Changed mission section hashes go through the router; repeated same-hash links explicitly reveal and focus their section. Monitoring focuses its heading on mount, including history navigation. The first writer lock can refresh a provisional session and remount the planner; the bounded presentation focus retry remains.

A fresh review confirmation requires a new snapshot identity after the save request, current evidence currency and successful browser persistence. A rejected write retains the prior snapshot without promoting it to a fresh success state. Memory-only reviews have an explicit label and no durable-save success mark.

## Phase 8 bounded extension

The original `missionObservations()` records, fixture identities, core evaluator, reserved historical evaluation fixtures and protocols remain unchanged. `LegacyObservation` preserves the engine boundary. The union adds discriminated absolute VO₂peak, reported sleep duration and a preflight-only cycling HR record. The existing envelope keeps its namespace; new record identities, source references, protocols and comparison windows explicitly carry `fictional-health-register-v2`/v2. `allMissionObservations()` is the one longitudinal register used for membership, identity, validation and snapshots. The legacy bridge rejects new quantities; descriptive comparisons validate their own matching endpoint, protocol, window, gravity, session, acquisition declarations, quality and equivalent diary periods.

New browser sessions use `initialRichMissionState()` and `parallax.mission.rich.v2`. The original `parallax.mission.v1` store remains accessible through `?legacy=1`, with no automatic reset or membership migration. Changes to source/interpretation versions make earlier plans/reviews stale while preserving their exact snapshots. Newly created rich snapshots are schema 2 and include all original dated records, five interpretations and scoped coverage. Schema 1 snapshots retain their original format and validate independently. Canonical HTML and JSON consume the same handoff object.

`missionChapter()` version `mission-chapters-v1` validates separate contexts at 20 December 2039, 28 June 2040, 29 June 2040 and 30 June 2040. Each projection filters the common register by timestamp before observation validation. Chapter routes mount no mission writer and dispatch no context transitions. Approach remains the active review. Back/Forward, reload and keyboard navigation follow the hash router. Surface crew-report provenance is separate from numeric assessment evidence. A fixed-choice planning request is saved only after a successful browser write and restored by a bounded validator; it authorises no test.

Intentional protected changes are limited to extending the mission envelope, validating the legacy bridge seam, selecting the complete register, source/interpretation versions, descriptive interpretation/coverage and versioned review validation. The previous 46-file byte-identity statement describes the old candidate only. A private per-file change manifest accompanies this candidate. No new runtime dependency, imagery or external data path was added.

Large rich-profile history uses a lossless `storageSchemaVersion: 3` shared-value envelope when expanded JSON exceeds 450,000 characters. It preserves all five reviews/designations under the unchanged 500,000-character save guard, including repeated evidence keys and monitored cutoffs. Backward-only references, exact envelope fields, structural/depth/node limits and a two-million-character expanded bound reject malformed/cyclic/bomb inputs before the ordinary state/snapshot validators run. Canonical snapshots and exports remain expanded, unchanged semantic objects. Smaller and legacy saves retain their original JSON shape. The maximum-history regression checks full decode equality.

Supplementary preflight gas-analysis, sleep and cycling records appear in dated chapter exploration. Active Approach membership initially includes the original preflight force reference, one original transit HR record and four new transit descriptive observations; the HR follow-up remains archive-only. Historical chapter exploration never adds supplementary records to active membership.

The team explicitly approved the Phase 8 budget decision after the full candidate measured 1,490,475 static bytes / 784,401 code-text-graphics bytes with its complete source-bound evaluation record (473 unit/scenario tests; 182 browser workflows). The new strict ceilings are 1,510,000 total and 800,000 code/text/graphics bytes. Photography, per-JavaScript-asset and fresh-entry limits remain unchanged. The original gate failure is retained as evidence; no passing result was claimed under the old ceilings.

## Phase 9 guided product experience

`?demo=full#mission/preflight` starts the full journey; `?demo=short#mission/health` starts the short route. `?demo=full#mission/resume` resumes the last requested step. Hash navigation, Back/Forward and reload use the same application routes and components. The guide is lazy and has no scientific evaluator. Its completion projection uses `missionOverview`, exact plan/run binding and committed ledger samples/events/receipts/acknowledgments. A current saved review must include the demonstrated monitoring event and acknowledgment. Chapter-inspection visits are explicitly separate from scientific completion and bound to the session UUID. The conclusion recalculates current facts; visits cannot replace evidence. The short route skips chapter exploration only.

The fixed demo profile adds `.guided.v1` to the mission key, writer lock, planning key and monitoring database. Both paths share that one bounded profile. It preserves existing unrestricted and legacy stores; repeated starts do not allocate unlimited profiles. The demo mounts the existing mission writer through chapter exploration without changing the active Approach context. Default unrestricted chapter exploration still mounts no writer. Exit returns to the ordinary product. Restart walkthrough clears only chapter visits after confirmation; Restart mission uses the original reducer generation reset and retains bounded histories and protected events. Storage limits and retention rules are unchanged.

Guided Start replay calls the existing controller start and explicit pause commands. The first sample is actually parsed and committed; paused samples remain historical. Next sample uses the existing deterministic command. The companion keeps the query profile and exact session/run identity and never acquires mission editing ownership. Retry editing reloads and requests the existing non-stealing lock; unavailable/held/failed acquisition reasons remain visible beside the disabled controls. Memory-only work cannot complete the guide.

Review policy `fictional-review-3` adds bounded oxygen-uptake, sleep, interruption and acquisition-limitation reasons. New and recovered current-policy reviews validate reason applicability against actual projections and monitoring. Historical enum meanings and snapshots remain unchanged. Rich cards and their inspectors share the actual exclusions. Summary rows include all relevant findings; planning requests remain a separate local information-planning record, never an obtained measurement or sent order.

The team explicitly approved Phase 9 ceilings of 1,530,000 total static bytes and 820,000 code/text/graphics bytes after a build measured 1,515,480 / 809,406 bytes before the final verification record. Photography stays at most 750,000 bytes, each JS below 400,000, and fresh mission-entry JS at most 350,000. Pinned Terser and Lightning CSS are build-only optimizers; runtime dependencies, target browser support, scientific validation and evaluation fixtures are unchanged. Complete source-bound verification measures the final record too.
